5070 Ti Dual — vLLM 설정 수정 및 측정

cyankiwi/Qwen3.8-27B-AWQ-INT4  ·  TP=2  ·  gpu2

보안 — 먼저 처리

HF 토큰이 평문으로 노출되었습니다. huggingface.co/settings/tokens에서 폐기 후 재발급하세요. API 엔드포인트도 인증 없이 열려 있습니다 — LiteLLM을 앞단에 두거나 --api-key를 적용하세요.

변경 요약

구분항목비고
추가 --max-num-batched-tokens 8192 가장 중요. 미지정 시 청크가 작게 쪼개져 GEMM 축소 + all-reduce 횟수 폭증
추가 --enable-prefix-caching 프리필이 전체 시간의 80%. 고정 스키마 재프리필 제거
추가 --served-model-name qwen3.8:27b 5090 서버와 이름 통일 → 클라이언트 코드 공용
수정 --max-num-seqs 32 → 8 동시성 32는 실측상 무의미 (처리량 +0.3%, TTFT 4.6배 악화)
수정 image: latest → v0.23.0-cu129 5090과 동일 버전으로 변수 제거 + 재현성
제거 PYTORCH_CUDA_ALLOC_CONF vLLM 메모리 프로파일링과 간섭 가능
제거 HF_TOKEN 평문 .env로 분리

docker-compose.yml

services:
  vllm-qwen:
    image: vllm/vllm-openai:v0.23.0-cu129          # latest에서 고정
    container_name: vllm-qwen3.8-27b-awq
    runtime: nvidia
    restart: unless-stopped
    ipc: host
    ports:
      - 8000:8000
    env_file:
      - .env                                # HF_TOKEN 분리, ALLOC_CONF 제거
    volumes:
      - ~/.cache/huggingface:/root/.cache/huggingface
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    command: >
      --model cyankiwi/Qwen3.8-27B-AWQ-INT4
      --served-model-name qwen3.8:27b
      --tensor-parallel-size 2
      --gpu-memory-utilization 0.90
      --max-model-len 8192
      --max-num-seqs 8
      --max-num-batched-tokens 8192
      --kv-cache-dtype fp8
      --enable-prefix-caching
      --enable-chunked-prefill
      --reasoning-parser qwen3
      --port 8000
      --host 0.0.0.0

.env 생성

cat > .env <<'EOF'
HF_TOKEN=hf_새토큰
EOF
chmod 600 .env
echo ".env" >> .gitignore

실행 절차

  1. 수정 전 로그 확보

    기존 max_num_batched_tokens 값이 이번 진단의 핵심 증거입니다. 재기동 전에 반드시 저장하세요.

    docker logs vllm-qwen3.8-27b-awq 2>&1 | grep -iE \
  "max_num_batched_tokens|Model loading took|GPU KV cache size|Maximum concurrency" \
  | tee before.txt
  2. 재기동 
    docker compose down && docker compose up -d
docker compose logs -f        # 기동 완료까지 대기
  3. 수정 후 로그 
    docker compose logs 2>&1 | grep -iE \
  "max_num_batched_tokens|Model loading took|GPU KV cache size|Maximum concurrency" \
  | tee after.txt
  4. 측정 — 전력 동시 관측 
    # 터미널 A
nvidia-smi --query-gpu=index,power.draw,utilization.gpu,clocks.sm \
  --format=csv -l 2

# 터미널 B
python vllm_bench.py --concurrency 8

판정 기준

전력 230W 이상

원인 확정 — 청크 분할. 텐서코어가 제대로 먹기 시작한 신호. TP=2 유지. 추가 조치 불필요.

전력 200W 유지

all-reduce 대기가 지배적. PP=2 A/B로 진행 — --pipeline-parallel-size 2, 청크 4096, seqs 16.

목표 수치

지표현재목표5090
프리필 (동시 1)2,120 tok/s2,900~3,4004,137 tok/s
배치 출력 (동시 8)117.5 tok/s170~200221.8 tok/s
TTFT p5011,029 ms4,000~6,0002,069 ms
96건 소요232 s140~165 s120 s
전력180~200 W230~250 W—

로그에서 특히 볼 것

Maximum concurrency for 8192 tokens per request: N — 엔진이 계산한 실제 동시성 상한입니다. N이 8 미만이면 KV 부족이 확정되므로 --max-model-len을 6144로 낮춰야 합니다.

다음 단계 (한 번에 하나씩)

  • PP=2 A/B — 전력이 230W에 못 미칠 경우. 배치 처리량 +20% 이상일 때만 채택하고, 채택 전 골든셋으로 출력 일치 검증
  • NVFP4 A/B — 프리필이 80%라 FP4 텐서코어가 공격하는 지점. 단 가중치가 0.8 GiB 크므로 GPU KV cache size를 함께 비교
  • MTP — --speculative-config '{"method":"mtp","num_speculative_tokens":3}'. 디코드만 개선되어 전체 8~10%
  • LiteLLM — vLLM 포트를 외부에 열지 말고 프록시만 노출. drop_params: false, request_timeout: 900

회신할 4가지

before.txt수정 전 로그 — 기존 청크 크기
after.txt수정 후 로그 — KV 캐시, 최대 동시성
벤치마크 출력python vllm_bench.py --concurrency 8 전문
전력 범위부하 중 power.draw 최소~최대
목표 수치는 추정입니다. 이 대화에서 계산 기반 추정이 실측에 여러 번 뒤집혔으니, 위 숫자도 측정 결과로 교정하시면 됩니다.
